# OpenRental 2.0 — planning and operational control

Baseline: 1.0.0 / 97ffdc7. Scope authorized on 2026-09-06.

## Product choices

1. Equipment planning: a date-based fleet timeline with category/location/search
   filters, a focused day, order links, overlapping-booking alerts and explicit
   maintenance/return holds. Include line-item assignments and overdue custody.
   Verify against real PostgreSQL fixtures, including timezone boundaries,
   multi-asset orders and denied roles. A forecast never overrides booking guards.
2. Personal work views: save named planning filters locally per signed-in user;
   share non-sensitive filters through URL state. Verify reload, switching users,
   corrupt storage, mobile use and keyboard navigation.
3. Operational control: expose failed/pending/manual-review lifecycle effects,
   existing business integrity findings and observed scheduled-job execution.
   Keep unscheduled/not-run state distinct from success. Protect jobs against
   cross-process overlap with PostgreSQL advisory locks and preserve errors.
   Verify two simultaneous runners, thrown errors, database outage and roles.
4. Delivery: no schema migration is planned. Validate types/lint/locales/tests,
   production build, API/database campaign, browser desktop/mobile and production
   readiness; back up and retain 1.0 for rollback before deploying 2.0.

Commercial pattern reference: Rentman's equipment timeline and shortage cues,
https://support.rentman.io/hc/en-us/articles/360013158280-Insight-in-Equipment-Availability
No commercial implementation or assets are copied. No new paid dependencies.

## Deliberate limits

Existing money, customer notification and rental-state writers retain their
rules. No real customer messages or funds in acceptance. No multi-replica claim
until lock behavior has actual database evidence. A monitor reports observed
execution in the current process; it is not a durable historical audit log.
Production data is a fresh independent instance, so historical source evidence
and isolated realistic fixtures inform this iteration; do not claim usage
analytics from a populated business deployment.

## Release evidence

Local acceptance on 2026-09-06: 1,459 tests in 144 files; TypeScript,
zero-warning ESLint, locale parity and production bundle passed. The full
isolated PostgreSQL/API suite passed, including 44 full-stack campaign checks.
The new `round_v2_planning.py` verifies exact line dates, multiple assets,
overlaps, cancelled rentals, overdue custody, combined work-order/rental holds,
Toronto DST boundaries, both required module permissions and private-effect
payload exclusion. `round_v2_job_lock.py` verifies contention between two OS
processes, release after exceptions and failure without a database.

Browser acceptance covers 390/768/1440 px, English/Chinese, date windows,
filters, order links, saved-view reload, malformed storage, another user's key,
quota failures, mobile details and keyboard activation. Zero page exceptions
and HTTP 5xx were observed. Saved views use stable user IDs, including accounts
without an email address. Production dependencies have zero audit advisories.

Reminder per-item failures and unconfirmed delivery now emit observed warnings;
the monitor never upgrades an unconfirmed SMS to delivery success. Current
process observations reset on restart. Hold dates remain conservative because
no trustworthy planned work-order completion date exists in the current model.

Production deployment/backup evidence belongs to the external 2.0 release
manifest and post-deploy report, populated only after those checks pass.

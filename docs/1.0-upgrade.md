# OpenRental 1.0 delivery ledger

Baseline: `dbafdba`, version 0.1.0. Started 2026-09-06.

## Product direction

A calm, industrial rental operations desk: graphite navigation, warm neutral
surfaces, teal actions, clear red exceptions. Show the work that needs attention
before aggregate reports. Keep the existing financial ledger and lifecycle.

Historical evidence in `internalWorkQueue.ts` records stalled maintenance and
unissued invoices. The dashboard currently substitutes zero for unavailable
statistics. `/health` does not query PostgreSQL. `verify` omits lint. Repository
CI does not run its real-path e2e harness. No GitHub deployments or matching
OpenRental Railway service were found during initial discovery.

Commercial references (patterns, not copied code):
- https://help.booqable.com/en/articles/4103695-how-to-view-availability-on-the-calendar
- https://support.rentman.io/hc/en-us/articles/360013158280-Insight-in-Equipment-Availability

## Acceptance gates

- [x] Runtime: database readiness, request correlation, secret redaction,
  explicit shutdown and deployment version evidence; failure-path tests.
- [x] Operations: actionable prioritized work queue, readable responsive shell,
  recoverable query failures, keyboard/table usability, bilingual copy.
- [x] Full stack: isolated PostgreSQL baseline + demo seed, lifecycle and money
  regression suite, desktop/mobile browser operations, production build.
- [x] Delivery: secure first administrator, reproducible image, gated deployment,
  post-deploy readiness and browser checks, documented rollback.
- [x] Maintenance: scheduled checks, bounded dependency upgrades only after
  validation, no silent success, durable evidence and continuation state.

## Boundaries

Only this isolated clone is writable. User authorized automatic deployment and
upgrades. Preserve customer records, money conservation, append-only issued
documents, role restrictions, and the yard timezone. Do not seed demo users into
an existing business database. Do not equate a version bump with acceptance.

## Ongoing maintenance limits

Inspect readiness and structured runtime errors hourly. Apply bounded bug fixes
and dependency patches only after the relevant acceptance gates; retain the last
successful deployment for rollback. Check backup schedules and recovery evidence.
The Codex continuation runs on the owner's machine and requires Codex execution
availability. Railway serves the app and schedules volume backups independently.
Migrate legacy railway.json to Railway's current project configuration before its
announced 2026-12-01 retirement. Do not enable multiple app replicas until cron
side effects have cross-instance locks.

External payment, email/SMS delivery and real business-data migration are not
validated by local fixtures. Keep those integrations unconfigured until genuine
business accounts and migration scope are supplied. Development-only drizzle-kit
transitive advisories remain; production dependencies are clear.

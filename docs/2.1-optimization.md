# OpenRental 2.1 — operational assistance, automation and performance

This release builds on 2.0 without a schema migration. It adds evidence-based daily priorities, a continuous-availability filter and bounded planner rendering, then reduces the cost of loading the application. It preserves the existing authorization, payment and rental lifecycle boundaries.

## User-visible changes

- The operations desk suggests the three highest-priority observed items. Ranking uses waiting time, the existing SLA threshold and a deterministic business-impact tie breaker. Every card explains its reason and shows waiting days and the target. Empty data produces no invented recommendations. These are rule-based suggestions, not an external LLM or autonomous customer/financial actions.
- Equipment planning can show assets available throughout the selected 7/14/28-day window. The screen renders 50 assets at a time; filters and totals still include the full result set.
- Successful business writes refresh the dashboard, schedule, queue, planner and operations status. A 150 ms debounce coalesces a burst of writes; inactive views become stale and active views refresh. No additional polling or mutation retries are introduced. A field inspection synchronization completion also triggers refresh.
- Language dictionaries load by namespace. Common English/Chinese shell text remains bundled. Fonts are self-hosted with their OFL license files. Field offline caches accept only successful same-origin GET responses.

## Measured performance

Baseline: commit `03a5f3c7a5f5cdc75f67e4988b14f6d1beada764`. Candidate and baseline use production bundles and the same isolated local database. Chromium, 1440×1000 viewport, 4× CPU slowdown, 100 ms simulated latency, 200,000 bytes/s download, cache disabled and service worker blocked; median of three cold loads per route. These are lab comparisons, not production real-user metrics or a promised SLA.

| Route | Encoded JavaScript before → after | Usable time before → after |
| --- | --- | --- |
| Login | 359,803 → 171,467 bytes (−52.3%) | 2,516 → 2,057 ms (−18.2%) |
| Operations desk | 412,276 → 235,085 bytes (−43.0%) | 3,610 → 3,051 ms (−15.5%) |
| Planning | 405,383 → 217,467 bytes (−46.4%) | 3,609 → 3,051 ms (−15.5%) |

The initial static JavaScript graph is 146,330 gzip bytes. React has explicit priority over chart dependencies in Rolldown's chunk groups, so optional charts do not enter the login dependency graph. Namespace splitting reduces transfer size but increases request count; the improvement is in bytes and loading time, not fewer requests. The two font files total 71,860 bytes.

With 5,000 synthetic open work orders, the queue query returns 28 rows / 4,634 serialized bytes instead of 5,003 rows / 538,575 bytes to the application, while exact category counts and SLA totals remain unchanged. The SQL window functions add local computation: median SQL-plus-summary time rose from 4.52 to 8.64 ms in five runs. This change bounds transfer and application memory; it is not a claim of lower database execution latency. At most 25 records per category (200 overall) cross the database connection. Age calculations now follow the application's yard timezone; midnight and DST boundaries are covered against PostgreSQL.

## Regression gates and reproduction

```sh
npm ci
npm run verify
npm audit --omit=dev
# Isolated test PostgreSQL only; the runner applies and seeds the test baseline.
OPENRENTAL_TEST_DB=openrental_e2e DATABASE_URL_TEST=postgresql://localhost/openrental_e2e bash e2e/run-all.sh
```

`verify` includes type checking, lint with zero warnings, bilingual key parity, unit tests, production build and the new `perf:budget` check. CI enforces an initial gzip JavaScript ceiling of 175,000 bytes, fonts below 80,000 bytes, no initial chart/PDF/calendar chunk and no Google Fonts stylesheet. Debug sourcemaps require explicit `GENERATE_SOURCEMAP=true`.

Local acceptance includes real PostgreSQL queue totals and caps, role denial, a 105-asset planner (50/50/5 pages), whole-window availability, an actual work-order UI write that refreshes the queue, bilingual route visits, mobile layouts, offline reload and automatic inspection synchronization with duplicate replay remaining one database record. Existing full API/database lifecycle tests remain required. Release deployment, exact revision, production browser and database proof are recorded separately with the release manifest; local results alone do not establish production completion.

## Release operation

Before deployment, take and restore a private PostgreSQL backup and create a Railway volume snapshot. Deploy the exact clean, pushed commit. Verify `/health/ready` version/revision, authenticated operational APIs, normal browser routes, session recovery and logs. No schema migration is required. The prior 2.0 deployment `7d3f4421-8c10-4eb5-9c69-affe8114d0dd` is the application rollback target. Restoring database data requires a separate incident decision and must never overwrite new business records automatically.

Hourly Codex maintenance requires this host and Codex to be available. Server-side operational schedules run on Railway independently. Changes still pass tests, backup and deployment verification; there is no unconditional dependency-update-and-deploy loop.
